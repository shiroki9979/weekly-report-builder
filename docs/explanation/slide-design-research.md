# 好的 Slide：新 Structured Layout 的研究參考

建立日期：2026-09-27

最後更新：2026-09-28

研究日期：2026-09-27

狀態：Research / Advisory；供設計討論，尚非核准規格

## 研究問題與結論

**好的 slide，能讓目標受眾在實際使用情境中，理解主要訊息、辨認支持依據，並知道這些資訊有何意義。** 對週報而言，通常是理解變化、判斷方案，或確認下一個承諾。這是本研究綜合後提出的工作定義，應以受眾理解情況驗證。

本文件將**口頭報告與自行閱讀視為同等重要**，範圍是 16:9 週報與未來 Structured Layout。建議先定義每種 layout 的溝通職能、內容關係與雙情境成功條件，再決定欄位、排列、字級與色彩。頁面是否好看，以及內容是否放得下，都是評估的一部分。

文中區分三種依據：

- **研究實證**：原始實驗或研究者對自身研究的整理；須保留樣本與情境限制。
- **專業指引**：TED、Duarte、ONS 與 W3C 等機構的第一方建議；不等同效果實驗。
- **本專案建議**：把研究與指引轉成週報設計假設；需經原型與實際內容驗證，沒有新增產品模式或更改既有規格。

## 哪些原則有依據

| 原則                 | 一手來源支持的內容                                                                                                                                                                                                                                                                                                                                                                                                                                    | 對 layout 的設計建議                                                                                       |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 把主要訊息說清楚     | **研究實證**：Garner 與 Alley 對 110 名工程系大學生的實驗中，整合多項多媒體原則的 assertion–evidence slides，在理解與延遲回憶上優於常見 topic–bullet slides。研究同時改變多項設計，不能只把效果歸因於標題。[原研究，2013](https://www.writing.engr.psu.edu/ae_comprehension.pdf)                                                                                                                                                                      | 主要標題容納可判斷的訊息，例如「試行版降低等待時間，建議擴大驗證」。章節名與工作流標籤放在次要位置。       |
| 減少不服務目的的處理 | **研究實證**：Mayer 整理的 coherence 原則支持移除無關材料；signaling 支持用提示揭露重要資訊的組織；spatial contiguity 支持把相關文字與圖形放近。[研究者章節摘要，2005](https://www.cambridge.org/core/books/abs/cambridge-handbook-of-multimedia-learning/principles-for-reducing-extraneous-processing-in-multimedia-learning-coherence-signaling-redundancy-spatial-contiguity-and-temporal-contiguity-principles/C98AB3A6CE760DD63C048936EA0B3B44) | 每個區域回答一個明確問題；標籤貼近對象；留白用來分組；強調色集中於需注意的差異。保留有助判斷的條件與例外。 |
| 設計閱讀順序         | **專業指引**：W3C 建議一致的頁面設計，並兼顧易讀字型、觀看距離與配套材料。[WAI 簡報指引](https://www.w3.org/WAI/teach-advocate/accessible-presentations/)                                                                                                                                                                                                                                                                                             | 共用標題、上下文、主要內容與註記的位置規則；由主訊息進入證據，再看限制。不同職能仍可有不同構圖。           |
| 在實際尺寸驗證可讀性 | **專業指引**：TED 要求在排練時確認最遠處觀眾讀得到文字，並保持背景與圖表清楚。[TED 舞台設計指引](https://www.ted.com/tedx/organizer-guide/prepare-speakers-and-program)                                                                                                                                                                                                                                                                               | 在預期投影條件及接收者閱讀 PNG 的尺寸分別檢查；縮圖、作者的大螢幕與沒有溢出，都不能單獨證明可讀。          |

研究範圍須特別留意：Garner 與 Alley 的實驗是工程學生觀看 MRI 技術教學，並非企業週報；Mayer 與 Moreno 的研究以多媒體教學及理解／遷移測驗為主。因此，將以上結果用於週報，是有理由的設計方向，仍需在實際受眾上驗證。[Garner 與 Alley](https://www.writing.engr.psu.edu/ae_comprehension.pdf)、[Mayer 與 Moreno，2003](https://www.researchgate.net/profile/Richard-Mayer-4/publication/253772914_Nine_Ways_to_Reduce_Cognitive_Load_in_Multimedia_Learning/links/57799b9908aeb9427e2c00b4/Nine-Ways-to-Reduce-Cognitive-Load-in-Multimedia-Learning.pdf)

**本專案建議**：美感應與溝通目的一起評估。字體、間距、對齊與色彩形成一致的視覺語言；邊框可分組，照片可提供情境，文字頁可承載精確敘述。每個元素都應有可說明的作用，整套頁面則需兼顧一致性與職能辨識。

## 雙情境：共用訊息骨架，分別驗證

**專業指引**：Duarte 區分現場投影 slides 與能離開講者獨立理解的 Slidedoc，並提出用補充文字形成閱讀版本。這是設計實務建議，沒有證明所有簡報都必須製作兩份。[Duarte：Slides 與 Slidedoc](https://www.duarte.com/blog/the-slides-you-deliver-versus-the-slidedoc-you-leave-behind/)

以下是本專案的設計建議：

| 面向     | 口頭報告                             | 自行閱讀                     | 共用的最低要求                     |
| -------- | ------------------------------------ | ---------------------------- | ---------------------------------- |
| 接收節奏 | 跟隨講者，需迅速定位正在談的內容     | 自行停留、跳讀與回查         | 訊息層級清楚、閱讀順序可辨認       |
| 說明密度 | 主要證據在畫面上，口述補充推理與例子 | 必要推理、名詞及條件需可取得 | 標題本身有意義，證據與結論對得上   |
| 上下文   | 可由前頁與講者鋪陳                   | 可能從單張 PNG 開始讀        | 對象、週期、指標單位與比較基準明確 |
| 完成條件 | 聽完後能說出本頁要點與影響           | 沒有講者也不會誤讀結論或限制 | 必要時能找到來源、下一步與驗證方式 |

**優先嘗試一頁分層**：主訊息可快速辨認，支持內容可逐項讀取，必要條件保留在可讀的註記區。如果這樣仍無法同時滿足兩種情境，可研究「同一資訊骨架的兩種密度版本」或配套閱讀材料；成本是內容同步與雙份驗證。這些是未來設計選項，現有產品沒有因此新增模式。

目前 Speaker Notes 顯示在 Stage 外，既有分享流程匯出 PNG。要讓單張輸出可獨立理解，必要資訊不能只留在 notes；若放不下，需拆頁或把閱讀材料一併交付。相關現況見 [Workshop preview](../../src/components/workshop/workshop-preview.tsx) 與 [匯出流程](../how-to/export-slides-to-team-deck.md)。

## 從資訊關係選 layout

本專案已將 Structured Layout 定義為服務反覆出現的溝通職能，並有 Weekly Overview、Evidence-backed Decision、Next Actions 與 Two-column Layout。[領域定義](../../CONTEXT.md)

**專業指引**：ONS 建議依資料中最重要的關係選擇圖表，例如比較、時間、分布與組成，並優先使用受眾熟悉的形式。[ONS：Choosing a chart type](https://service-manual.ons.gov.uk/data-visualisation/chart-types/choosing-a-chart-type)

以下關係表是對新 layout 的設計建議；「三欄」或「左右各半」可作為構圖結果，brief 應先說明內容之間的關係。

| 受眾要回答的問題         | 主要關係               | 可考慮的呈現方式                                          | 設計時應先確定                               |
| ------------------------ | ---------------------- | --------------------------------------------------------- | -------------------------------------------- |
| 本週最重要的變化是什麼？ | 主次、結果與影響       | Lead Outcome 加 Supporting Outcomes；已有 Weekly Overview | 哪一項值得最高優先？支持項目如何補充它？     |
| 為什麼採用這個方案？     | 同基準比較、裁決與依據 | 配對指標加解讀；已有 Evidence-backed Decision             | 比較口徑、成本與限制是否足以支持裁決？       |
| 接下來承諾什麼？         | 優先順序、行動與驗證   | 有序 Commitments；已有 Next Actions                       | 預期結果與 checkpoint 是否可辨認？           |
| 指標如何隨時間改變？     | 趨勢、事件與時間       | 折線，或呈現各期間發生量的柱圖                            | 是否有足夠時點？時間間距與缺值如何呈現？     |
| 卡在哪一個步驟？         | 順序、依賴與阻塞       | 流程／依賴圖搭配阻塞註記                                  | 箭頭表示順序還是因果？哪些節點真正影響結論？ |
| 選項有哪些差異？         | 多準則權衡             | 對齊維度的比較表或矩陣                                    | 準則是否一致？是否需要精確讀值而非看趨勢？   |
| 新方案具體改變了什麼？   | 前後差異、局部證據     | 同尺度的前後畫面，直接標註差異                            | 截圖是否聚焦且字可讀？差異是否可由畫面驗證？ |

新增 layout 前，先用真實週報證明現有格式不足以表達該關係。相同內容只換卡片形狀或顏色，通常不足以證明需要新增 Structured Layout。

### 把溝通目的轉成視覺構圖

以下是依前述 signaling、spatial contiguity 與一致性指引提出的**本專案設計建議**，用於比較候選構圖；它們不是已由研究證明的固定比例或樣式。

| 構圖面向   | 可採用的做法                                                           | 審查時觀察什麼                                       |
| ---------- | ---------------------------------------------------------------------- | ---------------------------------------------------- |
| 主焦點     | 用尺寸、字重、位置與留白，讓結論或主要證據取得最高優先                 | 多個大數字、色塊或標題是否同時爭奪注意？             |
| 對齊與分組 | 相關內容靠近；同類標籤、數字與比較項目沿共同基準對齊                   | 不讀完整句子，也能辨認哪些內容屬於同一組嗎？         |
| 留白與密度 | 留白用來區隔層級；空間優先給關鍵證據，再分配次要說明                   | 空白是否有組織作用？為塞入內容而縮字時，是否應拆頁？ |
| 字型與層級 | 為結論、支持文字、標籤／註記定義穩定角色，使用可讀字型及清楚的大小差異 | 長標題、中英混排與多位數值出現後，角色是否仍可辨認？ |
| 家族一致性 | 相同語義沿用色彩、間距與文字角色；構圖隨資訊關係改變                   | 讀者能否沿用前頁的閱讀方式，又辨認這一頁的不同目的？ |

### 資料與圖表的可信度

**專業指引**：ONS 要求長條／面積圖從零起點呈現；折線與散點圖可視目的調整範圍，可比圖表應維持一致尺度，雙 Y 軸須避免誤導。[ONS：Axes and gridlines](https://service-manual.ons.gov.uk/data-visualisation/guidance/axes-and-gridlines) 圖表文字需交代主要訊息、測量對象、範圍、時間與來源。[ONS：Chart text](https://service-manual.ons.gov.uk/data-visualisation/guidance/chart-text)

本專案建議每個數字保留足以解讀的基準，例如「上一週 12 分鐘 → 本週 8 分鐘」，並分清百分比與百分點。缺值、估計值或不同樣本需明示；美化後仍應得到相同判斷。現有 Comparison Metric 的條長按各指標自己的最大值計算，設計審查不可把不同指標的條長當成共同量尺。[現有計算](../../src/lib/metric-format.ts)

### 可讀性與無障礙是不同層次的檢查

- **文字對比**：WCAG 的一般文字及文字影像基準為 4.5:1，大字為 3:1；18 pt／14 pt 粗體是該標準的大字定義，不能直接當成投影最小字級。[W3C：Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
- **資訊辨識**：狀態與差異不能只靠顏色；需另有文字、形狀或標籤。[W3C：Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) 理解內容必需的圖形對鄰接色須有足夠對比，WCAG 對適用圖形的基準為 3:1；裝飾線不一概適用。[W3C：Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
- **完整交付**：W3C 亦建議提供可調整的無障礙材料、替代文字與結構。[WAI 簡報指引](https://www.w3.org/WAI/teach-advocate/accessible-presentations/)

本專案可先以關鍵文字 4.5:1 作為保守設計起點，再做投影及小尺寸閱讀檢查。HTML Stage 的標題語義、閱讀順序與 `aria-label` 不會成為 PNG 的結構；因此，視覺可讀且自足的 PNG，仍不能單獨證明完整無障礙交付。需要時應搭配可讀取的文字／資料或具語義的文件。這是依目前 [圖表元件](../../src/components/stage/evidence-decision-slide.tsx) 與 [PNG capture](../../src/lib/stage-capture.ts) 做出的產品限制判斷。

| 文字越少越好，講者會說的就全部刪掉               | **研究實證**具有條件：Mayer 與 Moreno 指出，沒有動畫時，同時提供口語和文字可能優於只有口語，不能把 redundancy 原則延伸成一律刪字。[原文，2003，Type 4](https://www.researchgate.net/profile/Richard-Mayer-4/publication/253772914_Nine_Ways_to_Reduce_Cognitive_Load_in_Multimedia_Learning/links/57799b9908aeb9427e2c00b4/Nine-Ways-to-Reduce-Cognitive-Load-in-Multimedia-Learning.pdf) 本專案保留獨立閱讀所需資訊。 |
| 每頁一定要放圖，或所有項目都不准使用清單         | 本專案不設此規則；圖應解釋關係或提供證據，有順序的承諾可使用清單。資料、引言與文字結論也能構成有用頁面。                                                                                                                                                                                                                                                                                                               |
| 一頁一個重點等於只能出現一項資料                 | 本專案將「重點」解讀為一個溝通目的；支持同一結論的比較、數個 Outcome 或有序 Commitments 可以共存。                                                                                                                                                                                                                                                                                                                     |
| 沒溢出、可以匯出，就代表內容品質合格             | Export Readiness 檢查內容與可捕捉條件；受眾是否理解、比較是否公平、兩種情境是否成立，需另行驗證。[現有定義](../../CONTEXT.md)                                                                                                                                                                                                                                                                                          |

## 虛構週報：同一訊息的兩種呈現

以下數值、樣本與決策均為虛構，只示範內容組織，不構成專案現況或新欄位規格。

**原稿**：「匯出功能進度」，下面等重排列「完成快取」、「修正三項問題」、「平均耗時 12 → 8 秒」、「下週持續觀察」。讀者仍需自行推斷這些活動有何影響，以及目前是否可擴大使用。

**共同骨架**：標題改為「試行版匯出縮短 4 秒，維持小範圍驗證」。主要證據為基準版 12 秒、試行版 8 秒；兩者都使用同一組 10 頁週報，各執行 20 次取平均。限制為「尚未測試大型圖片」；下一步為「週四完成大型圖片案例，再決定是否擴大」。

| 口頭報告版                                                                                                             | 自行閱讀版                                                                                                     |
| ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 主要區域突出結論與 12 → 8 秒；圖旁標示相同 10 頁樣本、每版 20 次平均；限制與下一步各一行。講者補充測試方法與實作經過。 | 保留相同結論與數值，在證據附近補充兩組條件一致的說明；標示測試日期、資料來源與限制，使離開講者後仍可理解判斷。 |

如果兩版共用單張輸出，方法說明必須在可讀空間內保留。若閱讀版擠到關鍵文字過小，應另頁補充；不能用縮字替代資訊取捨。這個例子展示的是待驗證方向，尚未證明任何特定構圖優於現有 layout。

## 未來 layout brief 與驗收提問

以下可作為新 layout 提案的起點；是本研究建議，尚未成為 schema 或 CI 規則。

### Brief 先回答的問題

1. **溝通職能**：受眾看完要理解、判斷或採取什麼？為何現有 layout 不足？
2. **受眾與情境**：哪些知識可假定？口頭報告與自行閱讀各在哪種裝置／距離發生？
3. **資訊關係**：主次、比較、時間、依賴、組成或其他關係，哪一個最重要？
4. **內容契約**：哪些欄位必要？數量範圍、單位、基準與來源如何呈現？有哪些不適用情況？
5. **視覺層級**：第一眼、接著、細讀時各應看什麼？圖形與空間如何支持這個順序？
6. **容量與退路**：最短、典型、最長真實內容如何呈現？超量時由作者精簡、拆頁或改用其他格式？
7. **雙情境交付**：單頁能否兼用？必要說明會在哪個可交付成品中保留？如何確保兩份內容一致？

### 建議驗證方法

| 檢查           | 可觀察的通過條件                                                                          |
| -------------- | ----------------------------------------------------------------------------------------- |
| 主訊息與目的   | 未參與設計的人能用自己的話說出本頁重點；其理解與 brief 一致。短暫觀看僅用來測主訊息定位。 |
| 證據與限制     | 能指出支持結論的依據、比較口徑與適用的限制；必要時可找到來源。                            |
| 口頭報告       | 在預期投影條件、正常講述節奏下，觀眾能跟上指向的位置，讀到關鍵內容。                      |
| 自行閱讀       | 只提供實際交付成品，沒有口頭補充和隱藏 notes，也能正確回答本頁要處理的問題。              |
| 內容變異       | 使用真實短／長文案、中文與中英混排、不同數字長度及合法最小／最大項目數；層級仍明確。      |
| 視覺與語義     | 必要文字與圖形對比足夠；移除色彩仍可辨識狀態；HTML 與交付成品分別檢查。                   |
| 匯出與閱讀尺寸 | canonical Stage 無裁切／溢出，實際 PNG 與預期閱讀尺寸亦可讀。兩者分別記錄結果。           |

現有 canonical capture Stage 為 **1280 × 720 CSS 像素**，PNG capture 使用 `pixelRatio: 2`；不可把 Stage 尺寸直接寫成最終 PNG 像素。既有 800 × 450 原型檢查也不取代正式匯出與實際閱讀驗證。[Stage 測量](../../src/lib/overflow-measurement.ts)、[capture 設定](../../src/lib/stage-capture.ts)、[歷史原型](layout-prototype.md)

建議以相同內容比較候選 layout 與現有格式，記錄「哪裡被誤讀、找不到什麼、哪一種情境需要補充」，再修改設計。單純偏好投票可補充風格判斷，不能取代理解測試。
